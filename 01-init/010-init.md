## 原始需求（用户原话）

> 我想把本地服务统一管理起来，运行web 前端启停本地某项web服务，查看当前日志

## 真实场景（2026-09-17 产品讨论后确立）

> 本节为「产品讨论模式」产出的场景澄清，**推翻了此前的多条假设**。
> 讨论全程原文见 [20260917_01_本地服务控制台产品讨论.md](20260917_01_本地服务控制台产品讨论.md)。

**一句话**：一台 Windows 服务器上跑着若干自建服务，出一键式的本机 Web 控制台，
让运维者不必再「找目录、记命令」就能重启服务、扫一眼日志。

**场景要素**：

- 一台 **Windows 服务器**，有固定 IP（用户口中的「本地」指的就是这台机器，不是开发机）
- 上面跑着若干**用户自建的服务**，每个都有 Windows 启动脚本（`.bat`）
- 这些服务**基本是 AI / LLM 相关服务**（推理、embedding、agent 之类）—— 这也是项目定名
  「AI Service Console」的依据：AI 描述的是被管理的对象，而非工具自身具备 AI 能力
- 每个服务都配置了**开机自启**
- 每个服务都会写**自己的日志文件**（标准日志输出）
- 服务故障（假死 / 崩溃）**靠他人告知**才发现
- 当前恢复方式：**RDP 登录服务器 → 找到服务目录 → 回忆并输入启动命令 → 重启**

**核心价值主张**：省掉「找目录、记命令」这两步。

**目标使用方式**：RDP 进服务器 → 在服务器本机浏览器打开控制台页面 → 点一下重启 → 扫一眼日志。

## 核心诉求（讨论后修正）

- 一个**在本机（服务器上）访问**的 Web 控制台，列出所有纳管服务
- 支持对单个服务执行「启动 / 停止 / 重启」操作
- 展示每个服务当前状态（运行中 / 已停止 等）
- **实时同步展示日志文件内容**（1 秒刷新一次）
- 服务配置可维护（名称、工作目录、启动脚本路径、日志文件路径）
- 控制台自身**开机自启**

## 明确排除的范围（用户主动砍掉）

| 排除项 | 说明 |
| ------ | ---- |
| 告警 / 主动通知 | 用户明确表示「只要能看能管就够了」，不需要主动推送 |
| 健康检查 / 端口探测 | 用户认为「服务是否正常，通过能否正常使用来验证」，由他自己判断 |
| 公网访问 | 用户最初希望互联网访问，讨论中主动收窄为内网 / 本机 |
| 鉴权 | 因收窄为内网访问，风险消解，首版不做 |

### 关键澄清：开发环境 ≠ 目标运行环境

初次询问时用户选择「三平台」，随后进一步澄清真实场景：

> **用户主要在 Windows 上使用该工具，当前这台 macOS 仅是他运行 Claude Code 编写代码的会话环境。
> 他另有一台 Windows 机器可以随时实际测试。**

这推翻了两条早期假设：

1. macOS 不是目标运行环境，**首版应做 Windows**
2. 原 PRD 建议的「先做 macOS」不成立，因为 macOS 只是开发机

**由此确立的开发/验证工作流：**

```text
代码在 macOS 上编写
  ├─ 纯逻辑层（配置 CRUD / 前端 / 日志读取）→ 可在 macOS 上先行验证
  └─ Windows 特定层（taskkill 进程树 / cmd.exe / 路径处理）
       └─ [需 Windows 验证] 在 macOS 上只能写不能验，须由用户拿到 Windows 上实测反馈
```

Task List 中每个任务必须标注 `[Mac 可验]` 或 `[需 Windows 验证]`，以便明确哪些产出
在交付时是已验证的、哪些是待验证的。
