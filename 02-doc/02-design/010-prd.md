## 1. 一句话定义

一台 **Windows 服务器**上的本机 Web 控制台，列出服务器上跑的所有自建服务，让运维者不必再「找目录、记命令」就能一键重启服务、扫一眼日志。

## 2. 背景与真实场景

- **「本地」的真实含义**：用户口中的「本地」= 那台 **Windows 服务器**（有固定 IP），不是开发机。这一用词在讨论中已澄清确认。
- **现状**：服务器上跑着若干用户自建的服务，每个都有 Windows 启动脚本（`.bat`）、都配了开机自启、都写自己的日志文件。
- **痛点**：服务故障（假死 / 崩溃「都有可能」）基本**靠他人告知**才发现；恢复路径是「RDP 登录服务器 → 找到服务目录 → 回忆并输入启动命令 → 重启」，麻烦在「找」和「记」。
- **核心价值主张**：**省掉「找目录、记命令」这两步**。
- **目标使用方式**：RDP 进服务器 → 服务器本机浏览器打开控制台页面 → 点一下重启 → 扫一眼日志。

## 3. 目标用户与使用方式

- **唯一用户**：工具作者本人（运维者），在 Windows 服务器上使用。
- **使用方式**：RDP 登录 → 本机浏览器访问控制台（默认 `http://127.0.0.1:3010`）→ 点操作 / 看日志。
- **开发/验证工作流（关键约束，延续 v2）**：
  - 代码在 macOS 上编写；用户在 Windows 机器上实际运行、反馈报错。
  - 纯逻辑层（配置 CRUD、日志文件 tail 读取、前端 UI）可在 macOS 上先行验证。
  - Windows 特定层（`taskkill` 进程树、`cmd.exe`、`.bat` 执行、编码）在 macOS 上**只能写不能验**，须 Windows 实测。
  - Task List 中每个任务标注 `[Mac 可验]` 或 `[需 Windows 验证]`。

## 6. 服务定义模型

单个「服务」对象字段：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `id` | string(uuid) | 是 | 服务唯一标识，系统生成 |
| `name` | string | 是 | 显示名称，用户自定义 |
| `workDir` | string | 是 | 工作目录（`.bat` 在此目录下执行；`path.resolve` 规范化） |
| `startScript` | string | 是 | 启动脚本路径（`.bat`）；建议绝对路径，相对则相对 `workDir` 解析 |
| `logFile` | string | 是 | 日志文件路径；建议绝对路径，相对则相对 `workDir` 解析 |
| `port` | number | 否 | 声明端口（仅记录展示，不用于探活） |
| `status` | enum | 系统 | 运行时状态，不持久化 |
| `pid` | number|null | 系统 | 当前进程 PID，运行时字段，不持久化 |
| `exitCode` | number|null | 系统 | 最近一次退出码，运行时字段 |
| `createdAt` / `updatedAt` | timestamp | 系统 | 配置时间戳 |

**相对 v2 的简化（已自行决策）**：
- 删除 `startCommand`（任意命令）→ 改为 `startScript`（`.bat` 路径）。启动动作从「执行任意命令」简化为「执行一个 `.bat`」，实现更简单、也匹配用户现状。
- 删除 `env` 字段：环境变量由 `.bat` 脚本内部自行管理，控制台不再注入。
- 删除 `autoRestart` 字段：用户未要求自动重启，服务本身已配开机自启。

## 7. 进程生命周期（Windows）

### 7.1 状态机

```
stopped ──启动──▶ starting ──宽限期(默认 5s/服务可配)内一直存活──▶ running
                    │                        │
                    │spawn 失败 / 宽限期内退出 ├─退出码=0──▶ stopped
                    ▼                        └─退出码≠0──▶ error
               start_failed

running ──停止──▶ stopping ──优雅终止/超时强杀──▶ stopped
```

### 7.2 各操作行为

| 操作 | 行为 |
|------|------|
| 启动 | 校验状态为 `stopped/error/start_failed` → 经 `shell: true`（Windows 下即 `cmd.exe /d /s /c`，见 §7.4 勘误）在 `workDir` 下执行 `startScript`（`.bat`）→ 置 `starting` → spawn 成功后在启动宽限期内保持 `starting`（带已用时长），宽限期满仍存活才置 `running`；spawn 抛错或启动宽限期内退出（见 §8.5 诊断）→ 置 `start_failed` 并展示诊断信息 |
| 停止 | 先 `taskkill /pid {pid} /T`（不带 `/F`，杀整棵进程树）→ 等待 5 秒 → 未退出则 `taskkill /pid {pid} /T /F` 强杀 → 置 `stopped` |
| 重启 | 等价于「停止（若在跑）→ 启动」，状态连续流转 |
| 异常退出 | 子进程自行退出：退出码 0 → `stopped`；退出码非 0 → `error`，记录 `exitCode` |

**Windows 停止语义**：Windows 无 POSIX 式 `SIGTERM` 优雅终止，`taskkill /T`（不带 `/F`）对控制台程序的效果接近直接终止。v1 的「优雅 → 超时强杀」两步是尽力而为，目的是**保证进程树被清干净、不残留孤儿进程**。

### 7.3 关键假设：`.bat` 阻塞式

本设计的 PID 跟踪与树杀**假设 `.bat` 是阻塞式**（服务进程前台运行、`.bat` 不退出）。理由：自建服务的启动脚本通常如此（如 `java -jar xxx.jar`、`node server.js`），这样才能靠 PID 跟踪存活、靠 `taskkill /T` 树杀。

若用户的 `.bat` 是「启动即退出」型（内部用 `start` 启动后台进程后自己退出），则 PID 已消失、孤儿进程无法树杀——需改用 `start /wait` 或 `call` 把 `.bat` 包装成阻塞式。此项在 §17 标为待确认。

### 7.4 Windows 特有坑

| 坑 | 应对 |
|----|------|
| 进程树残留（`.bat` 会 spawn 孙进程） | 停止一律 `taskkill /pid {pid} /T`（强杀加 `/F`） |
| 编码乱码（GBK/UTF-8） | 日志文件与启动诊断均以 Buffer 读，UTF-8 解码失败（出现 `�`）回退 GBK（`iconv-lite`） |
| 控制台窗口弹出 | spawn 加 `windowsHide: true` |
| 路径反斜杠 / 空格 | 统一 `path` 模块；`cwd` 用 `path.resolve`；不在命令里手拼路径 |
| `cmd.exe` 与 PowerShell 差异 | v1 统一 `shell: true`（见下方勘误），仍走 `cmd.exe`，不引入 PowerShell |
| `detached` 语义差异 | Windows 分支不设 `detached`，靠 `taskkill /T` 树杀 |

> **勘误（v3.1，2026-09-17）**：本表原写「v1 统一 `shell: 'cmd.exe /c'`」，该值**不能照抄**。
> Node 的 `child_process` 把**字符串形式的 `shell` 当作可执行文件名**，而不是「命令 + 参数」，
> 结果是 `ENOENT: spawn cmd.exe /c ENOENT`。正确写法是 `shell: true`——Windows 下 Node 内部
> 就是拼成 `cmd.exe /d /s /c "<脚本路径>"`，语义与原意一致，且由 Node 自己负责引号与转义。
> 验证依据：`server/test/win32.test.js` 中「shell:true 才能执行脚本文件；把 shell 写成
> "cmd.exe /c" 会 ENOENT」一例——反例断言 spawn 以 `ENOENT` 拒绝，正例用 `shell: true` 跑通并拿到 stdout。
> 实现见 `server/src/proc/win32.js`（`shell: true` + `windowsHide: true`）。

## 8. 日志能力（读文件 + 1s 轮询，非 stdout 捕获）

### 8.1 方案变更

- **旧方案（v2，废弃）**：`child_process` 捕获 stdout/stderr → 内存环形缓冲 → WebSocket 推送。
- **新方案（用户明确要求）**：每个服务**自己写日志文件**，控制台**读取并展示日志文件内容**，**约 1 秒刷新一次**（用户原话「1s 加载一次」）。

### 8.2 读取策略：全量 tail（非增量 seek）

- **选择「全量 tail」**：每次轮询从日志文件**尾部反向读最后 N 行**（默认 500 行，可配置）。
- **理由**：每次重新定位尾部，天然免疫「文件轮转（重命名）」和「文件被截断」——不依赖跨请求的 offset 记忆，实现简单、鲁棒。1s 一次的 tail 读对几 MB～几十 MB 文件都是毫秒级。
- **不选「增量 seek」**：增量 seek 虽高效，但必须维护每服务 offset 并处理「截断后 offset 失效」「轮转后 inode/句柄变化」，复杂度高；对「1s 刷一下看最近日志」的场景收益不大。列为 M3 可选项。

### 8.3 读取实现要点

- **大文件处理**：`fs.open` + `fstat` 取大小 → 从文件尾部按块（默认 64KB 起）反向读，凑够 N 行即停；不整文件 `readFile`。
- **单行超长保护**：单行超阈值（如 1MB）时截断并标记，避免异常日志拖垮前端。
- **编码（GBK/UTF-8，Windows 高频坑）**：读出的 Buffer 按「UTF-8 优先、失败回退 GBK（`iconv-lite`）」解码。日志文件编码通常从头到尾一致，此启发式在自用场景够用，需 Windows 验证。
- **轮转 / 截断**：因每次重新定位尾部读取，两者天然免疫，无需特殊处理。
- **路径不存在降级**：日志文件不存在 → 返回空 + 状态标记，前端显示「日志文件尚未生成（服务可能未启动或尚未产生输出）」；路径为目录 / 无读取权限 → 返回明确错误提示。

### 8.4 实时性：HTTP 轮询，不引入 WebSocket

- 前端每 **1s** 调 `GET /api/services/:id/logs?tail=500` 拉取日志尾部；服务列表状态每 **1–2s** 轮询一次。
- **决策理由**：用户明确「1s 加载一次」；单用户、本机访问、服务数量少，轮询开销可忽略；砍掉 WebSocket 去除一整块复杂度（ws 服务端 + 客户端 hook + 断线重连），符合「能看能管就够了」的极简定位。实时性由轮询节奏保证，足够满足「点一下重启、看状态变化」。

### 8.5 是否还捕获子进程 stdout（判断：需要，仅用于启动失败诊断）

**需要，但用途收窄**：正常运行时的日志一律以文件 tail 为准，**不再**用捕获的 stdout 做实时展示。但服务**启动失败时日志文件可能是空的**（服务没起来、没来得及写），此时用户看不到任何东西。

设计：
- spawn `.bat` 时捕获 stdout/stderr 到一个「启动诊断缓冲」（环形，约 200 行）。
- **启动宽限期**（`startupGraceMs`，全局默认 5s，可按服务覆盖）：AI 类服务加载模型要几十秒到几分钟，5s 的固定窗口不够用，所以做成可配。
- 若 spawn 抛错，或进程在宽限期内退出且退出码非 0 → 置 `start_failed`，把诊断缓冲 + `exitCode` 展示为「启动失败原因」。
- 若进程存活超过宽限期 → 视为启动成功（`running`），诊断缓冲停止更新（保留最近一段供排查）。宽限期内一直存活则保持 `starting`，UI 显示已用时长，让用户看得出「在加载」而不是「卡住了」。

这样既保留了「起不来能看到原因」的诊断价值，又让「日志以文件为准」的新方案成立。

### 8.6 过滤

- v1 前端对已展示日志行做关键字包含匹配（客户端过滤）。

## 9. 状态感知（运行状态如何判断）

- **运行判据 = 进程存活**（spawn 成功且未收到 `exit` 事件），**不依赖端口探测**。
- 这是用户的**明确选择**（排除健康检查）。其含义与已接受的限制：**假死**（进程还在但服务已不通）在页面上会显示为「运行中」，与正常服务无差别。用户明确表示「服务是否正常，通过能否正常使用来验证」，由他自己判断。
- PID 记录在运行时内存，不持久化。
- **已知边界**：控制台自身退出后，已启动的子服务（经 `cmd.exe` spawn）会继续存活（孤儿），新启动的控制台拿不到旧进程句柄，会将其显示为 `stopped`。v1 接受此边界，UI 在「状态可能不准确」时提示用户手动对齐（任务管理器 / `taskkill`）。

## 10. 控制台自身部署（Windows，含开机自启）

- **运行方式**：单端口部署。生产模式 = 后端 Express 托管「HTTP API + React 静态资源」，统一端口 `3010`（可配置）。开发模式 = Vite dev server（`5173`）代理 `/api` 到后端。
- **一键启动**：`start.bat`（装依赖 → 构建前端 → 启动后端 → 打开浏览器）。
- **开机自启方案对比（按可靠性排序）**：

| 方案 | 可靠性 | 部署成本 | 说明 |
|------|--------|---------|------|
| Windows 服务（winsw / node-windows 包装） | 最高 | 高（第三方包装 + 配置） | 登录前启动 + 服务管理器崩溃自动重启 |
| **任务计划程序（Task Scheduler）** | 高 | 低（原生 `schtasks`） | 可设「用户登录时」或「系统启动时」触发，可配失败重启 |
| 启动文件夹快捷方式 | 低 | 最低 | 仅用户登录后启动，无崩溃自动恢复 |

- **选择与理由**：**任务计划程序**（「用户登录时」触发 + 失败自动重启）。
  - 原生 Windows（`schtasks`），零第三方依赖，交付物只需一个注册脚本。
  - RDP 场景下用户登录是必然的，「用户登录时触发」即可满足——服务器重启 → 用户 RDP 登录 → 控制台自动拉起 → 浏览器打开。
  - 比启动文件夹可靠（后者无崩溃恢复）；比 Windows 服务轻（服务包装对 Node 进程生命周期管理是额外复杂度，纯自用不值得）。
  - 交付物：`install-autostart.bat`（用 `schtasks /create` 注册，触发条件「ONLOGON」，含失败重启）。若未来需要登录前就绪或更强崩溃守护，再升级为 Windows 服务（winsw）。

## 11. 安全与访问

- **默认绑定 `127.0.0.1`**，仅服务器本机可访问；绑定地址做成 `config.js` 可配置项（用户若想从局域网其他机器访问，改绑 `0.0.0.0` 即可，届时再评估是否加 token）。
- **无鉴权**（自用 + 本机访问，风险消解）。
- **过程记录**：用户初始希望「公网可访问 + 不设防」，讨论中明确「公网 + 不设防 + 能启停进程」三者技术上不成立（开放端口会被全网无差别扫描，等于把服务器交出去），用户据此主动收窄为「暂时内网使用」。公网访问 + 鉴权列为 M3 备选，M1 不做。

## 12. 边界条件与异常状态（需逐项验收）

| 场景 | 预期行为 |
|------|---------|
| `.bat` 路径不存在 / 工作目录不存在 | 状态 `start_failed`，展示 spawn 错误信息 |
| `.bat` 启动后立即崩溃 | `start_failed` / `error`，展示退出码 + 启动诊断缓冲 |
| 日志文件不存在 | 前端显示「日志文件尚未生成」，不报错 |
| 日志文件为目录 / 无权限 | 返回明确错误提示 |
| 停止时进程已自行退出 | 幂等：直接置 `stopped`，不报错 |
| 停止超时（>5s） | 自动 `/T /F` 强杀，置 `stopped`，记录「已强制终止」 |
| `.bat` 启动的服务被停止 | `taskkill /T` 连带杀孙进程，无孤儿残留 |
| 日志文件含中文（GBK） | 无乱码，正确显示 |
| 日志文件被轮转 / 截断 | tail 读仍正确展示最新内容，不报错 |
| 对「启动中」服务再次点启动 | 拒绝并提示「正在启动中」 |
| 无任何服务 | 列表空状态 + 引导「新增服务」 |
| 配置 JSON 损坏 | 启动时告警，降级为空列表并备份损坏文件 |
| 控制台重启后 | 配置完整恢复；运行状态重置为 `stopped`（§9 边界）；日志从文件重新读取 |
| 端口被占（3010） | 启动报错并提示改配置，不得静默失败 |
| 假死服务（进程在、服务不通） | 显示「运行中」（已知接受限制，见 §9） |

## 13. 非功能需求

| 维度 | 要求 |
|------|------|
| 性能 | 日志 tail 读取 + 1s 轮询不拖慢 UI；tail 读为毫秒级；轮询开销可忽略（单用户本机） |
| 可靠性 | 控制台崩溃不影响已启动的子服务；配置原子写；日志 tail 读对轮转/截断鲁棒 |
| 安全 | 默认仅监听 127.0.0.1，无外部端口暴露 |
| 兼容 | M1 = Windows（Windows Server / Windows 10/11）；Node ≥ 20；浏览器 Chrome/Edge |

## 14. 集成点

| 集成 | 用途 |
|------|------|
| Node `child_process` | 执行 `.bat`（`shell: true` + `windowsHide: true`，Windows 下即 `cmd.exe /d /s /c`；见 §7.4 勘误）；启动诊断捕获 |
| `taskkill`（系统命令） | Windows 进程树终止 |
| `iconv-lite` | 日志文件与诊断输出的 GBK 解码回退 |

无外部 SaaS / 云服务集成。**不再依赖 WebSocket**（改为 HTTP 轮询）。

## 15. 成功指标（自用，轻量）

- 重启一个服务的操作，从「RDP → 找目录 → 回忆并输入启动命令」降为「RDP → 登录 → 点一下」，耗时显著下降（核心价值「省掉找目录、记命令」）。
- 日志约 1 秒内看到最新内容，中文无乱码。
- 停止 `.bat` 类服务后无残留孤儿进程。
- 服务器重启 + RDP 登录后，控制台自动就绪。

## 16. 假设汇总（已自行决策，非阻塞）

1. `.bat` 为阻塞式（服务前台运行、脚本不退出）；若为「启动即退出」型需包装（见 §17 待确认）。
2. 日志读取用全量 tail（每次读尾部 N 行），不做增量 seek；编码 UTF-8→GBK 回退。
3. 启动诊断仍捕获 stdout/stderr，但仅用于启动失败场景，正常运行日志以文件为准。
4. 实时性由 HTTP 轮询保证（日志 1s、状态 1–2s），不引入 WebSocket。
5. 默认绑定 127.0.0.1，绑定地址可配置；无鉴权。
6. 服务数量不大（几个～十几个），UI 用列表布局。
7. 端口仅记录展示，不探活；假死显示「运行中」为已知接受限制。

| 「忘记启动」的真实成因 | 未细分 | 服务均已配开机自启，用户仍将其列为痛点，回答「都有可能」（漏配自启 / 自启失败）。可能该痛点已被自启解决，工具的活只剩「处理卡死的服务」和「看日志」 |

### 待确认问题（非阻塞，建议开发前口头确认）

1. **`.bat` 是阻塞式还是「启动即退出」型？** —— 决定 PID 跟踪与树杀是否成立；若为后者，需用 `start /wait` / `call` 包装。这是最需要确认的一项。
2. 服务数量大致多少？—— 确认列表布局是否够用。
3. 服务的具体形态（Node / Python / 原生 exe）？—— 决定树杀与编码的实测样本。
